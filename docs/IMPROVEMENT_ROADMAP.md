## Classification

Confirmed after reading the actual code: a real two-sided application (Laravel API + React SPA) with its own database, its own auth, and its own Docker stack — not a merge-into-umbrella candidate like the `small-candidate` repos elsewhere in this audit. No change to classification.

## Phase 4 (git hygiene) — start here, and start with one specific branch

Before any routine dependabot/renovate/snyk triage, diff `feature/security-docker-ci-and-tests` (14 commits ahead of `develop`, only 1 behind) against `develop`. Its commit subjects — `fix(security)`, `ci: run the docker quality gates on every push and pull request`, `build(docker): build every service from a local image`, `test: cover the api of the tasks and the authentication`, `chore(deps): update the dependencies and pin the platform`, `chore(security): take the credentials out of the repository`, `fix(fe): align the versions of the frontend and repair the build` — line up almost one-to-one with Phases 5, 6, 9, 10, and 11's open items in this audit. If even half of that holds up under review, merging it first could remove a large chunk of what the later phases would otherwise build from scratch. This was **not diffed** in Phase 3 (docs-only scope) — only commit subjects were read. Verify for real, then decide what's left to do in each later phase accordingly.

Also in Phase 4's scope: `master` (186 behind, 1 trivial unique commit) and `TransactionHelper` (146 behind, 1 trivial unique commit) are stale-and-likely-safe-to-close candidates; `refactor/readability-improvements` (26 behind, 2 commits) needs a normal review-merge-or-close decision. The ~33 dependabot/renovate/snyk branches are **not** merged in Phase 4 per the standing rule — they're Phase 6's job once the upgrade order is set, except: none of them have ever run through any CI (there isn't one), so "green" for any of them currently means nothing. **The committed `secrets/db_*` history removal is Approval Gate 1, kept explicitly separate from this phase's normal branch cleanup** — do not fold it into the general "clean up branches" work; it needs its own call-out and its own approval.

## Phase 5 (container baseline)

Rebuild all three Dockerfiles to the project's multi-stage standard (base → deps → build → test → runtime), fixing the `php.dockerfile` compiler-toolchain-in-runtime and `chmod 777` issues, giving `node.dockerfile` a non-root user and a real production build target instead of shipping the dev server, and — important — actually running the stack to find out for real whether the nginx `proxy_pass`-vs-`fastcgi_pass` mismatch (`docs/REPOSITORY_AUDIT.md` #7) breaks anything, rather than leaving it as a static guess. Before trusting any existing test run as the Phase 5 baseline, confirm what `phpunit.xml`'s currently-commented-out `DB_CONNECTION`/`DB_DATABASE` actually resolve to in the container — if it's pointed at a real Postgres service, fix that first (sqlite/in-memory for tests), independent of writing any new tests. Also run `php -l` on `UserSeeder.php` to confirm or disprove the suspected fatal namespace error (`TECHNICAL_DEBT.md` #3) before this repo's baseline run relies on seeded data.

## Phase 6 (upgrade to latest)

Follow Phase 2's upgrade order. The `laravel/framework` major bump (11→13, skipping 12) is simultaneously: the standing-decision-1 upgrade, and the only available fix for the critical CVE. Sequence matters here more than usual — `php-open-source-saver/jwt-auth` has already dropped Laravel 11 support in its own latest release, so the framework bump has to land before (or atomically with) the jwt-auth bump, not after. If the framework major bump changes this repo's own API/response contracts (error shapes, middleware behavior, Sanctum/JWT interplay) in a way that breaks existing frontend expectations, that's **Gate 5** territory — flag it explicitly if it happens, don't just absorb it silently. Also in this phase: resolve the `react`/`react-dom` version mismatch (pick 19.x for both, verify the SPA still builds and runs), and decide/record each of the many `vite`, `zod`, `tailwindcss`, `eslint` major jumps per standing decision 1 (upgrade, migrate, log in `CHANGELOG.md`).

## Phase 7 (dead code & restructure)

Concrete, named targets already found by static reading, not tooling-guessed: the duplicate `'api'` middleware-group registration in `bootstrap/app.php` (first one is dead), the `mongodb` compose service (zero consumers anywhere in the codebase), `@types/recharts` (deprecated, recharts ships its own types), the `App/` → `app/` casing drift once the framework upgrade is in and conventions are being re-aligned anyway, and the `UserSeeder.php` namespace bug once confirmed. The two static-analysis bugs in `TaskController`/`TaskRepository` (`show()`'s `authorize()` target, `findOrFail()`'s string-instead-of-exception) belong here as real bug fixes, each verified by a Phase 11 test written *before* the fix lands (so the test proves the current broken behavior, then proves the fix) — not guessed-and-fixed blind.

## Phase 8 (architecture)

The existing Repository+Service+Interface split for `Task`/`Auth` already gives DI-friendly, swappable boundaries — apply Clean/Hexagonal thinking by writing the ADR for *why* that boundary exists (external dependency: the database via Eloquent) rather than adding anything new. DDD bounded contexts are not warranted here (CRUD + reporting, no real domain invariants beyond "a user owns their own tasks," already enforced in `TaskPolicy`) — document that as a deliberate "don't apply" per the principles table in `CLAUDE.md`, not an oversight. No EDA need surfaced (no async cross-module reactions exist or are implied by the domain) — the `jobs` table exists but nothing enqueues anything; either wire up a real use for it or note it as unused scaffolding, Rasim's call. `TransactionHelper`'s misleading name (it's an exception-to-response mapper, not a DB-transaction wrapper) is a one-line rename worth doing in this phase for clarity, not a structural change.

## Phase 9 (hardening)

This is where most of the P0/P1 security items land: the unauthenticated `clear_cache`/`check/*` endpoints (add auth or, for the genuinely-public ones like `/health`, keep them public but remove the cache-clearing side effect from an unauthenticated path), the frontend's console-logged bearer token and `localStorage` storage choice, the plaintext compose-file DB credentials (wire up the already-written-but-commented-out `secrets:`/`load-secrets.sh` mechanism instead of re-inventing one), the hardcoded IDX cloud-workstation CORS origin (move to env), and adding PHPStan/Psalm (currently absent) alongside the existing `laravel/pint`. Also: write the currently-missing `openapi.yaml` as the single source of truth, retiring the manually-maintained Postman collection as a parallel contract (or explicitly keeping both and saying why, if Rasim wants Postman for manual QA convenience).

## Phase 10 (CI/CD)

Built from scratch — there is no pipeline today. Standard shape per `CLAUDE.md`'s CI/CD runner-time standard: cheap checks first (lint/format/secret-scan, parallel) → Docker `test` stage → build → image/dependency scan. Given this is the first CI this repo has ever had, expect the `feature/security-docker-ci-and-tests` branch (Phase 4) to already contain a draft of this — verify and adapt rather than starting from a blank file if that branch holds up under review.

## Phase 11 (tests)

Starting from near-zero: the only backend tests are the Laravel skeleton's `ExampleTest.php` files, and there is no frontend test runner at all. Priority order: (1) a test that pins down the real behavior of `GET /tasks/{id}` for both an owned task and a non-existent ID, resolving the two static-analysis-only findings in `docs/TECHNICAL_DEBT.md` (#4/#5) with an actual answer; (2) Auth flow (register/login/refresh/logout) given JWT is the only auth mechanism in active use; (3) Task CRUD + the report endpoint's aggregation logic; (4) a frontend test runner (`vitest` fits the Vite setup already in place) plus a handful of component/store tests, starting with the auth token-refresh interceptor given finding #19's exposure concern makes that code worth pinning down precisely. Regression baseline is whatever Phase 5 actually recorded — once `UserSeeder`/DB-isolation/nginx-config questions are resolved for real, not guessed.

## Not planned here

- **Deciding whether to wire up the `jobs` table / add a queue worker, or add Redis caching.** Both exist as unused scaffolding (a migration, a commented-out compose service) with no current consumer — adding a worker process or cache layer with nothing that needs it would be speculative (YAGNI). Revisit only if a real use emerges.
- **Deep DDD remodeling.** Per Phase 8 above — the domain is simple enough that the existing Repository/Service split is sufficient; a bounded-context/aggregate rework would be checkbox compliance, not a real improvement.
- **Automating Postgres backup/recovery into a production-grade story.** Flagged as a gap in `docs/TECHNICAL_DEBT.md` #18, but building real backup infrastructure is a platform/ops decision (closer to Phase 16's territory, if this repo is ever deployed to a real cluster) rather than something this application repo's own phases should invent unprompted.
